# Manual Windows CI build

The GitHub Actions workflow is **manual only** (`workflow_dispatch`) and builds a Windows x64 application bundle. It does not create a release, publish a repository package, sign binaries, or certify legal/runtime acceptance.

## Runner and toolchain

The job uses the official `windows-2025-vs2026` hosted runner label. On that ephemeral VM it:

- Verifies and updates the installed stable Visual Studio 2026 product through the official Visual Studio Installer, then requires VS 18.11.0 or newer and its official default MSVC toolset 14.50 or newer, as identified by `Microsoft.VCToolsVersion.default.txt`.
- Mirrors Flutter 3.47.7's stable `vswhere` workload/component queries and audits that selected Visual Studio instance's **bundled CMake**, never a substitute PATH executable. The bundled-CMake numeric baseline is **4.3.1**, matching the observed official VS 18.11 bundle `4.3.1-msvc1`; this is **not** a claim that standalone upstream Kitware CMake's latest release is 4.3.1. Plain stable versions and Microsoft's `-msvcN` suffix are accepted at or above that baseline; rc/alpha/beta/dev versions remain rejected. CI preserves the full raw version output and requires the real executable to advertise the Visual Studio 18 2026 generator.
- Only after the quick VS/MSVC/CMake checks pass, downloads the Windows SDK from Microsoft's `go.microsoft.com/fwlink/?linkid=2382519` source into a fresh UUID directory. The CI helper requires HTTPS redirects to remain on the approved Microsoft download host, validates the downloaded SHA-256 and Microsoft's Authenticode signature before execution, installs silently with the Windows SDK 10.0.28000 product-line `/q /norestart` mode, and then requires both SDK include version `10.0.28000.0` and servicing version 28000.2957 or newer, plus the required x64 headers, libraries and tools. It does not assume unverified optional feature IDs.
- The project selects the audited SDK from a CI-only environment value before `project()` initializes the toolchain, then records actual post-project `CHASTEADY_*` cache evidence. CI checks the real CMake executable/version, Visual Studio 18 2026 x64 generator, selected default MSVC compiler, and Windows SDK target against the preflight evidence.

Observed run `38771603533` on 2026-10-15 spent **2,270.74 seconds (37 minutes 50.74 seconds)** in the Visual Studio product update, which reached VS `18.11.12306.390` with default MSVC `14.51.36231`. The subsequent quick probe reported bundled CMake `4.3.1-msvc1` and confirmed Visual Studio 18 2026 generator support. That run stopped at the earlier incorrect 4.4.3 bundled-CMake floor, **before SDK downloading or native compilation began**; its elapsed time must not be described as SDK-install or compilation time. The corrected baseline retains the official vendor-supplied toolchain combination rather than patching the SDK or substituting another CMake executable.

All toolchain updates happen only on the disposable hosted runner. The workflow does not alter this workstation's PATH, trust store, proxy, security settings, or Visual Studio installation.

## Build and validation scope

`tools/ci_provision_flutter.py` downloads Flutter 3.47.7 stable only from Google's official Flutter release bucket. It rejects redirects, verifies the pinned archive byte count and SHA-256 before ZIP inspection, audits bounded safe members, and extracts to a separate new UUID directory. The font helper fetches the Noto Sans SC variable font by its pinned Google Fonts Git blob through the official GitHub API, verifies Git blob SHA-1/SHA-256/size and TrueType structure, and puts it only in an ephemeral build directory. The TTF binary is intentionally not part of the public source checkout; its SIL Open Font License and provenance text remain available.

### Early executable identity gate

The workflow provisions the Worker runtime, font and pinned Flutter archive **before** the long Visual Studio/Windows SDK update. It then invokes the existing helper's restricted `--preflight-flutter-only` mode with only the Flutter provision result, scratch root and a new isolated `--preflight-stage`. That mode reuses the pinned receipt/path checks, child-only environment and strict executable-version gate; it does not require a Microsoft toolchain report and cannot accept an artifact directory or other full-build inputs. Its receipt is explicitly identity-only, not native compilation, Worker testing, mathematical reproduction or runtime acceptance.

Both that early check and the later full build use the same version preparation: one supported plain `flutter --version` call, with private stdout/stderr capture, followed by `flutter --version --machine` whose **entire stdout must still be a single valid JSON document** with the expected stable versions. A cold extraction of the pinned official ZIP was observed to bootstrap its tool through `dart pub upgrade`, whose dependency-status stdout preceded the first machine JSON. On a second independent cold extraction, plain-version warmup followed by the strict machine query passed. No arbitrary prefix/tail, first-run notice, BOM or multiple-JSON workaround is accepted by the parser.

The official child-only `FLUTTER_SUPPRESS_ANALYTICS=true` switch selects NoOp analytics, independently preventing the first-run telemetry notice. Normal version/bootstrap operations can still write SDK caches and isolated tool state; this is not a zero-cache-write claim or a patched SDK. Failed commands expose only fixed stages/codes and bounded numeric/boolean output shape: byte counts, UTF-8/BOM, JSON-error position, actual process exit code and fixed launcher/exception/startup markers. Explicit `errno`/`errorCode` text can contribute only allowlisted OS constants; an English error message never supplies an inferred error code. Arbitrary stdout/stderr, credentials, command arguments and vendor/private paths stay runner-local. Quoted Windows paths in the bounded stderr sample are classified only lexically into fixed SDK/source/temp/cache/profile scopes, known SDK subtrees, character counts and optional fixed leaf IDs. No extracted path is resolved, opened or statted; unrecognized names, path text and environment values are never printed.

### Early UI gate and diagnostic-only dispatch

A second restricted mode, `--preflight-ui-only`, now follows the identity gate **before** the long Microsoft update. It requires the validated font result/scratch and a new stage, uses the same source-copy/font-hash and child-environment functions as the full build, rechecks executable identity, and runs locked pub, localization generation, analysis and all discovered Flutter tests. It cannot accept a Microsoft report, Worker manifest, math sidecar or artifact directory. Only real successful commands create its UI-check receipt; it performs no native/Web release build, window fixture, Worker test, packaging or runtime acceptance.

The manual workflow's optional boolean `ui_checks_only` defaults to false. Selecting true runs these early gates with a 15-minute job limit but skips Worker provisioning, VS/SDK updates, full builds and all artifact uploads. Normal full dispatches retain the existing 240-minute limit. This is a bounded cloud reproduction path, **not** a successful application build or a substitute for the later gates. A normal full dispatch still independently repeats UI analysis/tests and all original toolchain, source/runtime identity, Worker, packaging and inventory validation. No early receipt grants a later stage a pass.

Run `39020348075` stopped at `flutter_analyze` after the Microsoft update, with stdout 0 bytes and stderr 978 bytes; it never reached native compilation. Two source-identical local short/deep isolated-state probes passed without reproducing that failure. Those observations do not establish its root cause. The early UI gate and fixed diagnostic markers obtain cloud evidence without another blind long-toolchain cycle; they do not relax the exit-code gate. Follow-up run `39025741320` isolated the actual failing operation to SDK `dev` directory enumeration: the fixed list-directory/PathNotFound markers and explicit errno 3 matched, while two quoted SDK-dev paths measured 268/270 characters without an extended-length prefix. No raw path was published. A first shorter `cs-<UUID>` job directory and `f` scratch component reduced the observed SDK root from 155 to 116 characters, but run `39026116099` still failed at a different deeper SDK-dev path measuring 262/264 characters. That candidate was insufficient. A read-only full directory-metadata traversal of the same pinned local SDK measured maximum UTF-16 suffix lengths, including the separator, of 146 for `dev`, 87 for `examples` and 124 for `packages`; its actual 111-unit local root explains why local analysis could pass.

The provisioner now also places the complete SDK under compact `e/f-<UUID>/flutter` extraction containers, with unchanged separate UUID download/extraction isolation. The observed runner layout gives a 93-unit SDK root. Before extracting anything, it computes the three analyzer-subtree maximum directory suffixes from every audited archive member (including implicit parent directories) and rejects any combined path at or above 240 UTF-16 units. The build helper independently validates this numeric budget against the actual SDK root and fixed limit. This protects directory traversal plus the subsequent short pubspec filename; it is not a general certification of arbitrary file paths or all SDK subtrees. No SDK files are omitted or patched, no Windows long-path policy changes, and analysis/tests remain mandatory. Short-layout run `39027551158` passed the identity, locked pub, localization, analysis and test gates; full run `39027824791` independently repeated the UI checks and built Windows/Web, then failed at the separate native window fixture. The analyzer-path fix is verified, not a successful application bundle.

The full UI build pipeline runs, in order:

1. `flutter pub get --enforce-lockfile`
2. `flutter gen-l10n`
3. `flutter analyze --no-pub`
4. `flutter test --no-pub --reporter expanded`
5. `flutter build windows --release`
6. `flutter build web --release --no-web-resources-cdn --pwa-strategy=none`

Analysis and all discovered Flutter tests must succeed before either release build. Their fixed `flutter_analyze` / `flutter_test` stages and `CI_FLUTTER_ANALYZE_EXIT` / `CI_FLUTTER_TEST_EXIT` failure codes do not expose raw runner-local logs. Omitting either check cannot yield a successful bundle. Only successful execution sets the separate `ui_checks` facts in the build status and manifest; these are not desktop-window, player, browser, or video-export runtime acceptance. The job remains build-only in that sense. Flutter/Dart state and the audited `$git` shim are child-process scoped; Git and pub caches live under the runner's temporary build tree.

CI also enables the normally-off `CHASTEADY_BUILD_WINDOW_CHROME_SMOKE` target using the same audited CMake executable and existing VS2026 build cache, revalidates the configured toolchain, builds the standalone window-chrome fixture and runs it with a bounded owned process. It creates only its own Win32 owner/child windows; it does not enumerate, inject input into, or close an existing application. Its EXE/PDB stay under `native_smoke/Release`, outside the installed application output and ZIP. A separate `native_window_fixture` result explicitly means only this fixture passed: real Flutter app button interaction, Windows 11 Snap flyouts and multi-monitor DPI acceptance remain unverified. Configure/build/run failures expose only fixed stages and safe codes, not raw local logs.

### Supplemental preinstalled window-fixture diagnostics

Full run `39027824791` compiled the new Windows and Web releases, repeated UI analysis/tests, validated the configured production toolchain, and compiled the owned window fixture. The fixture then exited unsuccessfully during execution, so Worker building and ZIP publication did not run. Its raw output and numeric exit code were not present in that run's public diagnostic; neither the short runtime nor an unrelated portable MinGW failure identifies its cause.

Supplemental run `39033902496` used preinstalled VS `18.10.12224.181`, default MSVC `14.51.36231`, bundled CMake `4.3.1-msvc1` and SDK `10.0.26100.0`; configuration recorded compiler `19.51.36260.0`, VS18 generator and x64. Configure/build passed, then the real fixture exited 1 at source-bound `WF026` (child retains Flutter control hits), last-error 0, no PASS marker. The fixture used a `STATIC` child without `SS_NOTIFY`: Microsoft's documented default `WM_NCHITTEST` behavior is then `HTTRANSPARENT`, not the asserted `HTCLIENT`. Only the fixture style now adds `SS_NOTIFY`, giving the client-like baseline needed to test subclass delegation. Production window code, manifest, all 73 strict checks and their ID order stay unchanged; the source-hash pin and a static regression are updated explicitly. A new real probe must pass the remaining checks, and the full production gate remains required. This does not establish the previous full run's exact cause. See [Microsoft's static-control default message processing](https://learn.microsoft.com/en-us/windows/win32/controls/about-static-controls).

Both full builds and a new restricted probe now publish only a fixed fixture diagnostic schema: the actual uint32 exit value/derived hexadecimal value, a fixed check ID from the pinned authored fixture source, an optional DWORD last-error value, and bounded output shape. Only a whole, exact, ASCII single-line failure in the source-bound allowlist can supply a check ID; unknown or augmented text stays private. A last-error value may be stale and is not automatically a root cause. A PASS marker never overrides a nonzero exit, and diagnostic errors do not mask the process result.

Manual `window_fixture_only: true` selects a separate, 15-minute diagnostic path. It is mutually exclusive with `ui_checks_only`; selecting both fails before provisioning. The PowerShell `-FixtureProbeOnly` branch cannot combine with update/install switches, uses only an already installed stable VS2026 instance, its default MSVC, bundled CMake with the VS18 generator, and an installed complete Windows SDK. It performs no downloads, updates, or machine-configuration changes. Its exact report scope is `supplementary_diagnostics_only_preinstalled_toolchain`, with `production_toolchain_validated: false`; the normal production validator rejects this report.

Python `--window-fixture-only` accepts only that report and a new stage, rejecting Flutter/font/Worker/math/artifact inputs. It copies the same two C++ translation units, header and runner manifest unchanged, writes an isolated console-only CMake project with the same C++17/warnings/definitions/system libraries, explicitly selects the reported instance/toolset/SDK, and validates the real configuration before building and running the owned fixture. After descriptor validation it prints only allowlisted numeric selected versions; after actual cache validation and before building/running the fixture it also prints the actual compiler/SDK versions and fixed generator/architecture. These bounded public facts remain available if the fixture later fails; tool paths and raw output stay runner-local. Its fixed receipt records the actual preinstalled versions and keeps application, Snap, multi-monitor DPI, production-toolchain and artifact certification false. It does not configure a partial Flutter project or replace the full release gate.

This probe skips all Flutter/font/Worker downloads, Microsoft updates, release builds and artifact upload. Probe success cannot clear the failed production run or set the full build's fixture fact. A subsequent full run still requires the original latest stable VS/MSVC/SDK audits and the production fixture to pass.

For the Worker, CI provisions the current pinned isolated CPython runtime from the repository root, reruns all discovered backend tests, builds a fresh PyInstaller one-folder Worker from source, and runs the existing bounded stdio/loopback HTTP smoke and file-inventory checks. It never uses a prebuilt local Worker.

The private V9 math golden inputs stay local and are **not** uploaded, embedded, or rerun in CI. CI requires exactly one approved, unsigned local summary in `docs/` named `worker_math_golden_summary_20261015_<uuid>.json`. The sidecar is strictly checked against the current worker/math source inventory, CPython archive digest, exact latest-verified wheel identities, canonical error thresholds, three anonymous passing cases, and explicit local-only/no-input-path flags. A source, runtime, pin, schema, or measured-result mismatch stops the job. The manifest states `private_goldens_rerun_in_ci: false`; the local evidence is not represented as a CI golden rerun or cryptographic attestation.

## Artifact and claims

On success, the workflow uploads only:

- `ChaSteady-Windows-x64.zip`
- `ChaSteady-Windows-x64.zip.sha256`
- `ChaSteady-Windows-x64.manifest.json`

The app bundle contains the real `ChaSteady.exe`, Flutter Windows engine/data, freshly built one-folder Worker, offline web assets, README, `BUILD_STATUS.json`, original `LICENSE`, third-party notices, and selected license text files. License JSON manifests, non-license model files, caches, profiles, private build state, logs, credentials, and source media are excluded. The artifact expires after seven days.

Selected license notices, including SciPy's extensionless `LICENSE_DOP` redistribution notice, are copied byte-for-byte, without rewriting upstream text or exempting whole files/URLs from privacy checks. Drive-path detection requires a drive-token boundary, so the `p:/` suffix in `http://` and `ftp://`, or `s:/` in `https://`, is not mistaken for a Windows path. Actual drive/UNC paths (including those embedded in a URL), NUL bytes, repository/home markers, reparse points, invalid UTF-8 and oversized notices remain rejected. Fixed `bundle_license_texts`, `bundle_metadata`, `bundle_legal_notices` and `public_inventory` stages distinguish license copying, status JSON, top-level legal notices and the final scan; safe license/privacy error codes never include offending text or local paths. A license-only probe reaching the required-native-file guard after scanning is not a complete product inventory or an accepted build artifact.

The final inventory requires the exact declared font layouts: `web/assets/assets/fonts/NotoSansSC-wght.ttf` for Flutter Web and `data/flutter_assets/assets/fonts/NotoSansSC-wght.ttf` for the Windows CMake installation. Both retain the pinned full-font SHA-256 and the separate exact OFL identity; a same-basename font elsewhere cannot satisfy either required path.

All fixed final-inventory guards have explicit `CI_BUNDLE_*` error codes. File-specific failures can add only an allowlisted bundle category and SHA-256 of the complete relative path, not a raw filename, machine path, vendor output or credential. Unknown/augmented exception messages remain redacted.

The only reviewed `.npz` dependency-data admission is `Worker/scipy/stats/_sobol_direction_numbers.npz`: exactly 589,334 bytes with SHA-256 `4859931147d42ce465b8605cb277f957d98b839d03194fdf06579357906d193b`. Its audited source is the exact `scipy/stats/_sobol_direction_numbers.npz` entry of `scipy-1.18.1-cp315-cp315-win_amd64.whl`, archive SHA-256 `92c14f5bdbfb6216315ce33e78080474082de8b3830122ba97809bfbe65f75c0`; wheel RECORD, real frozen Worker bytes and the approved runtime report agree. Admission also requires this source identity to match both the current canonical provisioner pins and the validated runtime manifest. A wheel update requires re-auditing this entry. No NPZ/pickle loader is used, no dependency is deleted, all other `.npz`/`.npy` files remain forbidden, and private/profile/reparse checks still precede this narrowly bound data check.

`BUILD_STATUS.json` and the manifest explicitly keep `runtime_acceptance_verified`, `public_distribution_cleared`, signing, and legal certification false. **MIT applies only to original ChaSteady code**; bundled third-party terms remain applicable. A successful CI build is not a release or an end-user runtime acceptance test.
